CITYVET BACKEND DEVELOPMENT REPORT
Date: 2026-10-04
Project: Current CityVet dashboard (index.html)
Hosting target: Vercel serverless functions

1. EXECUTIVE SUMMARY
====================

The current dashboard was connected to a same-origin Vercel API backed by
Supabase PostgreSQL. The existing custom authentication/session design was
preserved: the API uses a restricted PostgreSQL login role, password hashes
stored in the database, and an HttpOnly signed-session cookie.

The dashboard's current data modules now have an API and persistence path for
their operational records. This includes:

  - Owners
  - Pets
  - Paravets
  - Census respondents
  - Households visited
  - Census animals
  - Stubs
  - Services
  - Programs
  - Program-day participants
  - Staff activity log
  - Public owner pre-listings

The existing sign-in, account, and barangay API work remains the authentication
and reference-data foundation.

The separate/older app.js clinic workflow is outside the active React
dashboard integration. Its browser-local storage is not connected to these
dashboard endpoints; operational work should use the React dashboard at `/`.

This is application and database integration work, not a deployment to a real
Supabase project. No API keys, database credentials, or JWT secrets were
available in the project folder, and no Vercel project was accessed or
deployed.


2. ARCHITECTURE AND CONNECTION FLOW
===================================

Browser dashboard
    |
    | same-origin HTTPS requests; HttpOnly session cookie
    v
Vercel serverless functions under /api/v1
    |
    | DATABASE_URL (server-side only)
    v
Supabase PostgreSQL, schema ekapon

The browser does not connect directly to Supabase and does not use a Supabase
anonymous key. This preserves the established server-side authentication and
database access pattern. Supabase's Transaction Pooler URL is intended for the
Vercel function's DATABASE_URL setting.

The dashboard uses a constrained JSONB record store for operational rows.
Every write goes through the API's explicit dataset allowlist; request data
does not determine a SQL table or column name. The JSONB storage was chosen as
a compatibility bridge because the current dashboard's data shapes differ
from the separate, unfinished Prisma model in schema.prisma.


3. DATABASE WORK
================

3.1 Fresh-install schema
-----------------------

Added db/000_ekapon_schema.sql as the fresh-install bootstrap. It defines the
existing authentication/account database requirements, reference data, and
the current dashboard persistence requirements.

The bootstrap includes:

  - ekapon schema, account and account-status types
  - Official barangay reference list (62 records)
  - Account, login-attempt, temporary-credential, audit, and settings tables
  - Password verification and temporary-password functions
  - Account key generation, mobile normalization, audit triggers, and
    account archive functions
  - Dashboard operational JSONB records with a fixed dataset allowlist
  - Import batch/item tracking used to support controlled import undo
  - Public pre-listing records and associated input constraints
  - A unique active-program-per-barangay-and-date index
  - Database role grants for ekapon_admin
  - Sample admin and encoder accounts with bcrypt hashes

The sample staff records are for initial/test setup only. Change their
passwords before public use. The migration source has no production credentials
or API-role password.

3.2 Existing-install dashboard upgrade
--------------------------------------

Added db/003_dashboard_records.sql for installations that already have the
earlier auth/accounts schema. It adds the dashboard record/import/pre-listing
tables, indexes, audit triggers, and database grants without dropping existing
tables or data.

db/002_fix_verify_password.sql remains the compatibility patch for older
auth-schema installations that need the password-verification fix.

db/001_create_api_role.sql remains the step that creates the restricted
ekapon_api login. Its password must be changed by the project owner before
running it; the chosen password must match the password in DATABASE_URL.

IMPORTANT: Do not apply the fresh-install schema on top of an existing
installation. Follow the fresh-install or upgrade path in README-BACKEND.md.

3.3 Record and access model
--------------------------

The dataset names accepted by the new records API are:

  owners, pets, paravets, respondents, households, animals, stubs, services,
  programs, participants

Records have a stable string/numeric UI id, a JSON object body, and an
archived flag. IDs are constrained to 1-100 characters; each incoming record
is limited to 20 KB; API record batches are bounded.

This is persistence, not a completed normalized veterinary data model. The
database does not yet enforce all domain-specific relationships or field rules
for owners, pets, services, programs, and participants. Row-level
tenant/barangay access policies have not been implemented.


4. API ENDPOINTS IMPLEMENTED/AVAILABLE
=======================================

Existing API endpoints retained:

  GET    /api/v1/health
  GET    /api/v1/barangays
  POST   /api/v1/auth/login
  POST   /api/v1/auth/first-signin
  POST   /api/v1/auth/set-password
  POST   /api/v1/auth/logout
  GET    /api/v1/auth/me
  GET    /api/v1/accounts
  POST   /api/v1/accounts
  GET    /api/v1/accounts/{key-or-id}
  PATCH  /api/v1/accounts/{key-or-id}
  DELETE /api/v1/accounts/{key-or-id}
  POST   /api/v1/accounts/{key}/reset-password
  POST   /api/v1/accounts/archive

Dashboard data endpoints added:

  GET  /api/v1/records/{dataset}
       Supports page, pageSize and archived=false|true|all.
       Returns data, page, pageSize and total. Archived rows include an
       _archived marker when archived=all is requested.

  POST /api/v1/records/{dataset}
       Upserts records supplied as { records: [...] }.
       Used by dashboard program and physical-stub creation.

  POST /api/v1/records/{dataset}/archive
       Archives/restores records supplied as { ids: [...], archived: boolean }.

  POST /api/v1/records/{dataset}/import
       Persists a CSV import batch and records prior row values so an import
       can be undone safely.

  POST /api/v1/records/{dataset}/undo-import
       Restores a prior import only when imported rows have not subsequently
       changed. Repeated undo and undoing another staff member's import are
       rejected.

Activity endpoints added:

  GET  /api/v1/activity
       Lists activity entries for authorized staff.

  POST /api/v1/activity
       Writes an activity entry for the signed-in staff member.

Public pre-listing endpoints added:

  POST /api/v1/prelistings
       Accepts owner name, mobile, official barangay, program, and 1-10 pets.
       Returns a public reference value.

  GET  /api/v1/prelistings
       Lists submissions for authorized Admin/Encoder accounts.

Dashboard record writes, archive operations, imports, undo operations,
activity reads/writes, and staff pre-listing reads require an Admin or Encoder
session and same-origin write protection. Public pre-listing submission
requires no staff session, but its values are validated on the server.

5.1 API client
--------------

Updated api-client.js to:

  - Probe /api/v1/health to determine whether the API is reachable.
  - Use same-origin credentials so the HttpOnly session cookie accompanies API

The dashboard import selector was expanded to expose the supported dashboard

Existing browser-local import history and the last-import pointer still

The generated submission response reference is shown to the user. The public

8. SETUP STILL REQUIRED FROM THE PROJECT OWNER
==============================================

No API keys or database credentials were present in the folder. The code
changes do not require a Supabase anon/public key. To connect this project to
the owner's Supabase and Vercel environments:

  1. Create or select the Supabase project and determine its region.
  2. In Supabase SQL Editor, apply the correct SQL path:
       New database:
         db/000_ekapon_schema.sql
       Then, for either path:
         Set a strong password in db/001_create_api_role.sql and run it.
       Existing prior auth/accounts database:
         Apply db/002_fix_verify_password.sql only if needed, then
         db/003_dashboard_records.sql.
  3. Change the initial admin and encoder passwords before public use.
  4. Configure Vercel's root directory and function region as described in
     README-BACKEND.md.
  5. Set Vercel server-side environment variables:
       DATABASE_URL
         Supabase Transaction Pooler connection string (normally port 6543),
         using the ekapon_api role and the exact password set in SQL.
       JWT_SECRET
         A unique random value at least 32 characters long.
       NODE_ENV
         Set to production by the deployment environment.
       ALLOWED_ORIGINS
         Leave blank for the same-origin deployment; configure only if another
         trusted origin must access the API.
  6. For local live testing, copy .env.example to .env.local and enter local
     or Supabase DATABASE_URL plus a separately generated JWT_SECRET.
  7. Run the SQL/database-backed integration suite and test the deployed
     health, login, read, write, archive, import/undo, and pre-listing flows.

Do not send database credentials or JWT secrets in chat. Enter them directly
into the local environment file and Vercel's Environment Variables settings.
Never commit .env.local.


9. KNOWN LIMITATIONS AND FOLLOW-UP WORK
=======================================

  - The dashboard operational storage is JSONB, not the final normalized
    domain schema. Domain constraints, relational links, advanced reporting
    queries, and domain-specific validation need requirements and a future
    migration.
  - The current Prisma schema is a separate, unfinished data model and is not
    used by the API. It must be reconciled before adopting Prisma for these
    operational records.
  - PostgreSQL row-level security is not implemented. Current API checks enforce
    role access and Paravet record scoping by assigned barangay.
  - CSV import history and the latest undo pointer remain browser-local UI
    metadata. Clearing browser storage can remove the UI's reference to an
    import batch, although the database maintains the batch data.
  - Existing localStorage/demo records do not automatically migrate. Retained
    data must be exported and imported deliberately after review.
  - Some tables in the current dashboard are primarily seeded views and do
    not have full standalone record-entry forms. Their records can be loaded
    through CSV import or the API. Program and physical stub creation are
    supported by existing UI forms.
  - Notifications, report basket selections, display/theme settings, the
    existing browser-local backup/restore utility, and some quality/import
    history UI state remain browser-local utilities. The new database export
    is separate and is not a restore mechanism.
  - Public pre-listings store personal information. Retention, deletion,
    privacy notice, access policy, and any applicable consent requirements
    must be confirmed with the organization.
  - Public pre-listing needs production abuse controls (Vercel WAF/rate limit,
    CAPTCHA, or an equivalent policy) before it is advertised publicly.
  - Login timing for unknown account identifiers and temporary-password
    delivery by SMS/email are existing documented hardening limitations.
  - Demo-mode fallback intentionally remains. Staff must verify that the API
    is live and that real records load before entering production data.


11. DASHBOARD ROLE AND ADMINISTRATION UPDATE
============================================

This section records the subsequent role-based dashboard implementation and
supersedes earlier descriptions of the staff roles as simply Admin/Encoder.
The current implementation is in the publishing clone and remains uncommitted
and undeployed; the database migration has not been applied to Supabase.
The owner previously deployed the earlier backend connection and health-check
changes; this statement applies only to the dashboard role redesign described
in this section.

11.1 Role mapping and access
---------------------------

The agreed role names and migration mapping are:

  - Existing Admin accounts become SuperAdmin.
  - Existing Encoder accounts become Admin.
  - Paravet remains Paravet.

SuperAdmin has full dashboard access, staff account administration, access to
the system controls and database export, and can toggle maintenance mode and
feature availability for Admin and Paravet roles.

Admin is the City Vet encoder/reporter role. It can work with operational
records, field operations, reports, data-quality checks, and data imports. It
cannot administer staff accounts or change system controls.

Paravet navigation is restricted to census encoding and masterlist access.
The records API only permits Paravet writes to respondents, households, and
animals; owners and pets are read-only masterlist datasets. API record
queries, archive operations, import operations, and import undo enforce the
assigned barangay. Upserts include a database-side conflict condition so a
concurrent write cannot replace a different barangay's row.

The Paravet check is an application/API authorization check against the record
JSONB barangay field. PostgreSQL RLS has not been configured. This is an
important remaining security architecture task before the project claims
database-enforced multi-tenancy.

11.2 Database installation and migration
-----------------------------------------

Fresh database setup:

  1. Run db/000_ekapon_schema.sql. The account enum already contains
     SuperAdmin, Admin, Paravet, and User, plus the system-maintenance and
     role-feature tables.
  2. Run db/001_create_api_role.sql after setting the role password.
  3. Replace sample staff passwords before production use.

Existing database upgrade:

  1. Confirm that this is the intended Supabase project and that a current
     database backup exists.
  2. Apply db/002_fix_verify_password.sql only if the earlier installation
     needs it, then db/003_dashboard_records.sql if dashboard persistence is
     not present.
  3. Apply db/004_dashboard_roles.sql exactly once. It renames the existing
     account enum values and creates the maintenance and role-feature tables.
  4. Deploy the matching API/frontend code only after the migration succeeds.

Do not run db/004_dashboard_roles.sql against a new database: the fresh schema
already uses the new role values. Do not run db/000_ekapon_schema.sql against
an existing database. The migration was not executed by this development
session and requires the project owner's action in the correct Supabase
project.

11.3 Navigation, dashboard, and analytics UX
--------------------------------------------

The dashboard navigation is reorganized under Workspace, Operations,
Registry, Insights, Data management, Administration, and Public services.
Visible routes are filtered by role and by SuperAdmin feature switches.
SuperAdmin controls are rendered in Settings. Maintenance mode blocks regular
Admin/Paravet access while keeping the SuperAdmin management path available.

The participation funnel and program panels are moved from the main dashboard
to the Reports/analytics view to reduce dashboard density. The reports view
adds live-record monthly activity, a comparison of the latest three months
with the preceding three months, an interpretation, upcoming-program count,
and a cautious linear planning estimate. It excludes browser demo seed rows.
The estimate is withheld unless at least 10 dated live records across at
least 3 distinct months exist; it is a planning signal, not a forecast
guarantee or audited KPI.

At sign-in, the dashboard offers to return to the last allowed section, with
the dashboard as an alternative. Navigation is grouped and restricted
according to role. A native browser beforeunload confirmation is used for
leaving the signed-in dashboard; browsers do not support a dependable custom
close-tab modal.

11.4 SuperAdmin database export
-------------------------------

The GET /api/v1/admin/backup endpoint is SuperAdmin-only. The Settings panel
downloads a JSON export containing application dashboard records, sanitized
account rows, barangay reference data, public pre-listings, audit history,
and system/role controls. Password hashes and sensitive credential keys are
excluded from the export. The export is intended as an offline backup and
does not provide an import/restore path.

This database export is independent from the pre-existing browser-local
backup/restore utility in Settings. The latter only operates on localStorage
and must not be described as a Supabase database backup.
