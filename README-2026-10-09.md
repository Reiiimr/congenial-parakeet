## 5. Implemented census submission workflow

### Database

- `db/005_census_submissions.sql` creates `ekapon.census_submissions` with a UUID, actor, barangay, label, JSONB records, status, reviewer, review timestamp/note, and indexes.
- `db/006_census_submitter_retention.sql` adds `submitter_name` and changes the submitter foreign key to `ON DELETE SET NULL`.
- Both migrations are applied to the current staging database according to the user’s confirmation and the subsequent integration-test connection.
- The new table is a staging/review layer, not a replacement normalized registry.

### API and data controls

- `POST /api/v1/census/submissions`: Paravet-only submission API, validates record datasets and assigned-barangay names, and stores the batch as pending.
- `GET /api/v1/census/submissions`: Paravets list their own submissions; Admin/SuperAdmin can list city-wide.
- `GET /api/v1/census/submissions/{id}`: Paravets can view their own submission; Admin/SuperAdmin can review any submission.
- `PUT /api/v1/census/submissions/{id}`: Admin/SuperAdmin approve or reject. Approval writes all records to `dashboard_records` in the same transaction as the review decision.
- Existing `POST /records/{dataset}` and archive paths now require Admin/SuperAdmin. Paravet import routes stage census rows; Paravet undo applies only to the Paravet’s own pending submission.
- Approved record IDs are replaced on approval if a record with the same dataset/ID exists. This behavior is a remaining high-priority decision and integrity concern (see below).

### Dashboard UI

- Paravet census form is attached to the existing Census section. It captures a household head, visit date, and a list of animals.
- Admin/SuperAdmin review panel is attached to Data quality. It shows pending submissions and their JSON records, and offers approve/apply or reject with an optional note.
- Paravets see a simple recent-submission status list.
- Owner pre-listings remain separate. The ZIP’s optional owner mobile/PIN login has not been added.

## 6. Open decisions and gaps before pushing

The following are not resolved by the passing tests. Resolve product/operational policy first, then implement and retest any resulting changes.

### P0 — must decide and address before release

1. **Cross-barangay record-ID collision on approval.**
   - Submission records are checked against the submitter’s barangay.
   - Approval upserts by `(dataset, record_id)`.
   - If that ID already belongs to an approved record from another barangay, the current approval path could replace it despite the submitted record’s barangay being correct.
   - **Recommendation:** Reject the approval atomically if an existing matching ID has a different barangay. Do not permit override until an explicit Admin override policy, reason requirement, and audit behavior are designed.
   - Add an integration test where an approved record exists in Barangay A, a Paravet in Barangay B submits the same dataset/ID, and approval is denied without changing the original.

2. **Approval is currently whole-batch replacement, not review-before-merge.**
   - One “Approve and apply” action writes every row.
   - Existing same-ID records are replaced; the reviewer sees submitted JSON but no structured before/after comparison.
   - Per-record keep/replace/merge choices are not implemented.
   - **Decision:** Is approval allowed to replace an existing record, merge only empty fields, keep the approved version, or require a per-record choice?
   - **Recommendation:** Start with safe defaults: new records may be approved; same-ID matches require explicit comparison and reviewer choice; cross-barangay match is always blocked. Record decisions and notes in audit history.

3. **Form completeness and canonical census contract.**
   - The new UI form submits household and animal data only; it does not create a respondent record or all existing census fields.
   - Existing census/import records use additional fields such as respondent name, animal count, condition, program interest, source, and census date. Exact import schemas vary by dataset.
   - **Decision:** Define a canonical form: required person/household fields, animal details, date/source, respondent relationship, optional fields, consent/privacy notice, and validation.
   - **Recommendation:** Agree on a field/data dictionary before expanding the UI or applying the ZIP’s normalized schema.

4. **Pending form lifecycle.**
   - The form submits immediately; no draft/save-for-later, edit, withdraw, or resubmit flow is exposed in the UI.
   - The API can append to a pending submission using the same UUID, but the form does not retain/reuse that UUID for later editing.
   - A Paravet can delete their own pending submission through the undo-import path, but the UI does not offer that action.
   - **Decision:** Can Paravets edit/withdraw pending submissions? Can rejected submissions be corrected and resubmitted, or must they create a new submission?
   - **Recommendation:** Define the allowed state transitions (`draft` if needed → `pending` → `approved` or `rejected`; optional withdrawal/revision) and retain immutable review history.

5. **CSV importer UX for Paravets.**
   - Census-dataset imports by Paravets are now staged, but `importer.js` still describes an import as applied/merged/replaced and offers restore-point/undo language.
   - This can mislead users into thinking approved records were changed.
   - **Decision:** Keep Paravet CSV census import, or disable it until the workflow is redesigned?
   - **Recommendation:** If retained, show “submitted for review,” link the UUID to the submission status, clarify that no approved record changed, and provide only a supported pending-submission withdrawal action.

6. **Feature-control consistency.**
   - `server/api-dispatch.ts` currently associates census API routes with the `operations` feature.
   - Admin review UI is surfaced in the Data quality section, which is associated with `data-quality`.
   - A SuperAdmin can therefore disable one feature while the UI/API authorization expectations may differ.
   - **Decision:** Should census review be controlled by Operations or Data quality?
   - **Recommendation:** Make navigation, client state, dispatcher feature tag, and API tests use the same feature decision.

### P1 — resolve for a dependable operational launch

7. **Structured review view and feedback.**
   - Current detail display is raw JSON; the list shows label, barangay, submitter, and record count.
   - Paravets see basic status but not the reviewer name, timestamp, or review note.
   - Decide whether reviewers need field-level comparison, filters/search, and whether submitters should receive rejection notes and resubmission instructions.

8. **Decision notes and accountability.**
   - Review note is optional for both approval and rejection.
   - Decide whether rejection must include a reason and whether replacement/override approval must require a note.
   - Confirm how long reviewer accounts must remain undeletable; `reviewed_by` currently uses a restrictive foreign key while `actor_id` is nullable after migration 006.

9. **Domain validation and duplicate handling.**
   - The API validates dataset allowlist, record IDs, per-record size, and assigned-barangay text. It does not yet enforce the full domain data dictionary for all dataset fields.
   - Decide required dates/counts, allowed species/sex/condition values, duplicate household/animal rules, maximum submission size, and rules for identifiers shared across datasets.

10. **Visibility and correction after approval.**
    - Paravets cannot directly edit/archive approved rows; corrections require another pending submission and Admin action.
    - Confirm that this is intended and define how corrections reference the record being corrected.

11. **Retention, deleted accounts, and audit.**
    - Migration 006 retains submitter name and nulls actor ID on submitting-account deletion.
    - A deleted submitter cannot see their submissions through the own-submissions filter.
    - Reviewer deletion remains restricted by reviewed submissions.
    - Decide retention period, export/backup treatment, whether deletion should be blocked instead of anonymized, and who can access historical records.

12. **Database-level enforcement.**
    - The API login can access application tables via the project role but no PostgreSQL RLS policy was added.
    - Barangay checks are primarily application-level.
    - Decide whether API-only enforcement is acceptable for this release. For a stronger boundary, design database policies/functions and test them under the exact runtime database role before enabling.

13. **Owner / User scope.**
    - Owner pre-listing remains separate and personal data is handled outside census review.
    - ZIP mobile/PIN owner login is unapproved and would require owner-specific row privacy, authentication, account recovery, consent, and data retention decisions.
    - Confirm owners remain excluded from this push and whether pre-listings need a separate review/retention policy.

14. **Normalized schema scope.**
    - The current census workflow stores staged JSONB records then applies them to the existing JSONB registry.
    - The ZIP migrations require missing normalized tables and diverge from the agreed role policy.
    - Decide whether the normalized schema is a later project phase. Do not apply ZIP `005/006` as-is to this branch’s database.

### P2 — future improvements (not implied to be push blockers unless policy requires them)

- Add PostgreSQL RLS or stored procedures for tenant/role boundaries, after a careful migration plan.
- Add an immutable review/change history with before/after snapshots and actor/reviewer identity.
- Add notifications to submitters when submissions are approved/rejected.
- Add offline/draft support for field collection if operationally needed, with conflict-safe synchronization.
- Add accessibility/usability tests and responsive browser checks for the new form and review panel.
- Add data export/backup coverage for census submissions and their reviewer history; verify restore procedures separately.
- Add Vercel WAF/rate limiting or CAPTCHA before public pre-listing launch; establish personal-data retention/access practices.
- Address previously documented backend risks before public production: unknown-account login timing, public endpoint abuse, temporary credential delivery, and any outstanding security review.

### Suggested decision prompts

Copy/paste one prompt at a time and answer with a specific rule:

**Record collision policy**
> When an approved record has the same dataset and record ID as a submitted census row, what should Admin approval do? Choose: (1) reject the whole submission if barangay differs and require explicit per-record review for same-barangay matches (recommended), (2) always replace same-barangay matches but reject cross-barangay matches, or (3) another precisely specified rule. > Please define the required fields for a valid Paravet digital census form: respondent/household information, animal details, visit date, source, counts, contact/consent fields, allowed values, and any optional fields. Which existing dataset fields are canonical, and which should be retired?

**Imports**
> Should Paravets be allowed to import census CSVs? If yes, should each imported file be one pending review submission, and should we replace the importer’s current “applied/undo” language with “submitted for review” and a tracked status/withdrawal action?

**Feature permission**
> Should census review be controlled by the Admin “operations” feature toggle or the “data quality” toggle? Choose one source of truth for the UI, API dispatcher, and tests.

**Review notes and retention**
> Must rejection include a reason? Must approval that replaces a record require a note? How long must submitter, reviewer, and submission history be retained, and should account deletion be blocked or anonymize names?
